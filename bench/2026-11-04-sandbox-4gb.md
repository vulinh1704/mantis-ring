# 4 GB per sandbox: the self-tests, two GitHub tasks at once, and the VM's memory (4 Nov 2026)

On 4 Nov at about 20:00 ICT the owner raised each sandbox's memory from 3 GB to 4 GB. At 3 GB, ray-so (a Next.js 16 app) ran out of memory in 1 of 2 looks ([2026-11-04-nextjs-memory.md](2026-11-04-nextjs-memory.md)). This note records what was measured on the VM after the change: the self-tests, a re-check of ray-so, the B2 repository's look with one screen size at a time, and how much of the VM's memory two sandboxes at once leave.

- **When:** 4 Nov, 13:14–13:25 UTC (20:14–20:25 ICT).
- **Where:** the VM at `e9c598d`, every sandbox under gVisor (`runsc`) with 4 GB of memory and no swap, 2 CPUs and 512 processes.
- **The change** (`061f5f4`):
  - `LIMITS.memory` is `4g`, and Docker gets `--memory 4g --memory-swap 4g`. The tmpfs folders keep their sizes: they cap each folder and set no memory aside.
  - The live log still warns at less than 1 GiB free before the first look. That is what a look needs, whatever the limit.
  - `/admin/config` accepts `maxRunning` 1 or 2; 3 was allowed with 3 GB sandboxes.
  - The containment memory check reads its cap from `LIMITS.memory`, Docker and the host cgroup instead of a fixed 3,072 MB.
- **`e9c598d`** adds `scripts/ring.sh mem`, which reads the VM's memory as `deploy` (free and the cgroups; `deploy` cannot run `docker stats`).

- **`deploy.sh --selftest`** (restart at 13:15:28 UTC): on the VM's Node 22, `agent-loop --unit` 129/129 and `app-api` 86/86, then containment 18/18 and scenes 20/20.

## The VM's memory

`scripts/ring.sh mem` reads, as `deploy`, `free -m` and each cgroup's `memory.current`, `memory.peak` and `memory.max`.

| | Idle (13:12 and 13:21 UTC) | During the pair (150 s from 13:22:12 UTC) |
|---|---|---|
| RAM (16 GB VM) | 15,986 MB in all; 709–723 MB used, 15,262–15,277 MB available | available at least 11,755 MB (13:22:42 UTC), read once a second; the two looks did not overlap |
| All containers together (the sandboxes and the proxy) | 6 MB (the proxy alone) | at most 3,460 MB (13:22:41 UTC) |
| Swap | 8,191 MB, none used | none used (a sandbox has no swap: `--memory-swap` equals `--memory`) |

The services, by their cgroups:

| Cgroup | Now (13:24 UTC) | Most since it started | Limit |
|---|---|---|---|
| The app (`mantis-ring.service`, restarted at 13:15:28 UTC) | 25 MB | 79 MB, through the self-tests and the three tasks | 2,048 MB (`MemoryMax=2G` in its unit) |
| The proxy container | 6 MB | 66 MB | 128 MB |
| Caddy | 15 MB | 20 MB | none |
| Docker | 49–54 MB | 81 MB | none |
| containerd | 1,624 MB | 1,648 MB | none |

containerd's figure is almost all page cache from the images: `free` counts it under buff/cache (4.4 GB), not as used, and the kernel can take it back.

**The worst case fits.** Each limit below is enforced by a cgroup, so it cannot be passed:
- two sandboxes at 4,096 MB each: 8,192 MB;
- the proxy at its 128 MB;
- the app at its 2,048 MB;
- the rest of the host as measured idle, about 700 MB.

That is about 11,070 MB of the 15,986 MB, which leaves about 4.9 GB, and the page cache can be reclaimed on top of that. Three sandboxes would come to about 15,170 MB and leave about 0.8 GB, so `maxRunning` stops at 2.

**One case to watch.** `scripts/deploy.sh --selftest` runs `ring-selftest` beside the app, not through its queue. It checks that the VM is idle before it starts, but it does not hold back tasks that start meanwhile. The containment suite runs up to two sandboxes at once. So once GitHub runs are open, two tasks and a deploy self-test could hold four sandboxes, up to 16 GB. With only sample runs open, which install nothing, memory is less of a risk, but the self-test's timed checks would share the 4 vCPUs with live tasks. Until a deploy holds the queue, run `deploy.sh --selftest` with public runs closed. Otherwise run the suites with `ring.sh selftest`, which waits for running tasks and holds new ones.

**Update, 4 Nov, 14:59 UTC (21:59 ICT):** since `8583f0a`, a deploy holds the queue: `deploy.sh --selftest` runs the containment, scene and agent-loop suites through the app, one `POST /admin/selftest` each, as `ring.sh selftest` does. It takes effect on the VM with the next deploy.

**Update, 4 Nov, 16:15 UTC (23:15 ICT):** more exactly, a deploy's self-test step holds the queue, not the whole deploy. The restart is not held: it interrupts any run in progress. Since `98e2319`, `deploy.sh` checks again that no task runs or waits and no self-test waits or runs just before it swaps the tree in and restarts, not only before it copies the code, so only a run that starts in the few seconds between that check and the restart is caught (README, "A deploy interrupts runs in progress" under Known limits). The VM still runs `2a52e4e`: none of this is on it until the next deploy.

## How to repeat

The tasks cost nothing: the spend guard refuses the first model call.

```bash
scripts/ring.sh mem 150 > mem.txt &      # start the sampling first
scripts/ring.sh run '{"repo":"https://github.com/raycast/ray-so","visionModel":null,"caps":{"maxUsd":0.000001,"maxPromptTokens":1000},"label":"4gb-pair:ray-so"}'
scripts/ring.sh run '{"repo":"https://github.com/coreui/coreui-free-react-admin-template","visionModel":null,"caps":{"maxUsd":0.000001,"maxPromptTokens":1000},"label":"4gb-pair:coreui-react"}'
scripts/ring.sh logs | grep '<task id>'  # the before the baseline look: and baseline look usage: lines
```

`ring.sh run` prints the owner link. Keep that line out of logs and files.
